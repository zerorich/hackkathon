# 5. КЛЮЧЕВЫЕ USER FLOWS

# FLOW 1. Авторизация ученика

1. Пользователь вводит телефон/email в зависимости от выбранного OTP-канала.
2. Client вызывает запрос OTP.
3. Backend создаёт OTP challenge.
4. Для hackathon код либо реально отправляется внешним сервисом, либо возвращается/логируется в demo mode.
5. Пользователь вводит OTP.
6. Backend проверяет OTP.
7. Если пользователь новый — создаёт User.
8. Возвращает access token + refresh token.
9. Клиент получает `/auth/me`.
10. Если профиль не заполнен — открывает onboarding.

Ошибки:

- invalid identifier;
- OTP expired;
- invalid OTP;
- too many attempts;
- rate limited;
- user blocked.

---

# FLOW 2. Вступление ученика в класс

1. Ученик получает invite code от преподавателя.
2. Открывает Join Class.
3. Вводит код.
4. Backend проверяет существование и активность класса.
5. Создаёт membership STUDENT.
6. Dashboard начинает показывать предметы и leaderboard этого класса.

**Конкурентность:** повторные одновременные запросы Join не должны создать несколько membership.

Нужна уникальность `(classId, userId)` и транзакционно безопасная операция.

---

# FLOW 3. Преподаватель создаёт класс

1. Teacher открывает Classes.
2. Нажимает Create class.
3. Указывает название, grade и optional description.
4. Backend создаёт класс.
5. Создаёт teacher membership.
6. Генерирует уникальный invite code.
7. Teacher получает страницу класса.
8. Может скопировать invite code.

**Конкурентность:** invite code должен быть уникальным.

---

# FLOW 4. Преподаватель создаёт предмет и тему

1. Teacher открывает класс.
2. Создаёт Subject.
3. Создаёт Topic.
4. Указывает:
   - название;
   - описание;
   - difficulty;
   - optional source text/context.
5. Topic появляется ученикам.

Для MVP не требуется сложная учебная программа.

---

# FLOW 5. AI генерирует challenge

1. Teacher или Student выбирает Topic.
2. Нажимает Generate Challenge / Start AI Practice.
3. Frontend отправляет параметры:
   - topicId;
   - difficulty;
   - questionCount.
4. Backend создаёт AI generation job.
5. Job получает контекст Topic.
6. Внешний AI возвращает структурированный набор вопросов.
7. Backend валидирует структуру.
8. Сохраняет Challenge + Questions + Options.
9. Challenge получает статус READY.
10. Frontend получает готовый challenge.

Для hackathon допустим polling.

Статусы генерации:

- PENDING
- PROCESSING
- READY
- FAILED

**Нестандартная логика:** AI output нельзя считать валидным. Backend обязан принимать только структуру, соответствующую контракту.

Если AI недоступен, должен существовать demo fallback: заранее подготовленный набор вопросов.

---

# FLOW 6. Ученик проходит challenge

1. Ученик открывает challenge.
2. Нажимает Start.
3. Backend создаёт Attempt со статусом IN_PROGRESS.
4. Клиент получает вопросы без correctAnswer.
5. Ученик отвечает.
6. Ответы могут отправляться по одному либо одним payload при finish.
7. Ученик нажимает Finish.
8. Backend атомарно завершает Attempt.
9. Сервер сравнивает ответы с правильными.
10. Рассчитывает:
    - correct count;
    - incorrect count;
    - accuracy;
    - score;
    - duration;
    - XP reward.
11. Обновляет StudentStats.
12. Обновляет TopicProgress.
13. Обновляет streak.
14. Обновляет leaderboard-derived данные.
15. Возвращает Result.

**КРИТИЧЕСКАЯ КОНКУРЕНТНОСТЬ.**

Два одновременных `finish` запроса не должны:

- дважды начислить XP;
- дважды засчитать attempt;
- дважды изменить streak;
- дважды обновить статистику.

Finish должен быть идемпотентным на уровне бизнес-операции.

**РАСЧЁТНЫЙ МОДУЛЬ:**

- score;
- accuracy;
- XP;
- streak;
- topic mastery.

---

# FLOW 7. Ученик создаёт дуэль

1. Ученик завершает challenge.
2. На Result нажимает Challenge Friend.
3. Backend создаёт Duel.
4. Создаётся share code.
5. Duel фиксирует:
   - challengeId;
   - challengerId;
   - challengerAttemptId;
   - status WAITING.
6. Пользователь копирует ссылку/код.
7. Друг открывает ссылку.

Пример deep link:

`/duel/{shareCode}`

Для MVP реальный Telegram/WhatsApp API не нужен: достаточно Web Share API / Copy Link.

---

# FLOW 8. Друг принимает дуэль

1. Пользователь открывает duel link.
2. Если не авторизован — проходит auth.
3. Backend возвращает preview:
   - challenger;
   - subject;
   - topic;
   - difficulty;
   - question count.
4. Нажимает Accept.
5. Backend проверяет:
   - duel WAITING;
   - пользователь не challenger;
   - opponent ещё отсутствует.
6. Устанавливает opponentId.
7. Duel становится ACTIVE.
8. Создаётся Attempt для opponent.
9. Пользователь проходит тот же Challenge.

**КРИТИЧЕСКАЯ КОНКУРЕНТНОСТЬ.**

Если несколько пользователей одновременно пытаются принять один shareCode, победить должен только один.

Операция `accept duel` требует блокировки/Serializable transaction.

Ошибки:

- DUEL_NOT_FOUND
- DUEL_EXPIRED
- DUEL_ALREADY_ACCEPTED
- CANNOT_DUEL_SELF
- CHALLENGE_NOT_READY

---

# FLOW 9. Завершение дуэли

1. Opponent завершает attempt.
2. Backend рассчитывает результат.
3. Получает challenger attempt и opponent attempt.
4. Определяет победителя.

Правило MVP:

1. выше score;
2. при одинаковом score — выше correct answers;
3. если одинаково — меньше durationMs;
4. если всё одинаково — DRAW.

5. Duel становится COMPLETED.
6. Сохраняется winnerId либо null для DRAW.
7. Обновляется duel статистика обоих игроков.
8. Начисляется bonus XP победителю.
9. Клиент показывает duel result.

**КРИТИЧЕСКАЯ КОНКУРЕНТНОСТЬ:** duel нельзя завершить дважды и нельзя дважды начислить winner bonus.

**РАСЧЁТНЫЙ МОДУЛЬ:** winner resolution + bonus XP.

---

# FLOW 10. Leaderboard

1. Ученик открывает Leaderboard.
2. Выбирает период:
   - weekly;
   - all time.
3. Backend возвращает игроков класса.
4. Сортировка MVP:
   - XP descending;
   - completed challenges descending;
   - userId/createdAt как стабильный tie-breaker.
5. Текущий пользователь отдельно помечается.

Leaderboard не должен принимать rank от клиента.

Для hackathon допускается вычисление из агрегированных stats.

Redis можно использовать для кэша leaderboard.

---

# FLOW 11. Teacher analytics

1. Teacher открывает Dashboard.
2. Backend возвращает:
   - total students;
   - active students;
   - completed attempts;
   - average accuracy;
   - total challenges;
   - duel count;
   - average XP;
   - weak topics.
3. Teacher открывает конкретный Topic.
4. Видит:
   - attempts;
   - unique students;
   - average accuracy;
   - completion count;
   - strongest/weakest students;
   - distribution по результатам.
5. Teacher открывает Student.
6. Видит:
   - total XP;
   - streak;
   - completed challenges;
   - accuracy;
   - topic progress;
   - recent attempts.

**РАСЧЁТНЫЙ МОДУЛЬ:** агрегированная статистика.

# 6. БИЗНЕС-ПРАВИЛА

## 6.1. Challenge

Challenge может быть начат только если:

- status = READY;
- challenge активен;
- topic не архивирован;
- пользователь имеет доступ к классу.

После READY набор вопросов не меняется для уже созданных попыток/дуэлей.

---

## 6.2. Questions

MVP поддерживает:

- SINGLE_CHOICE;
- TRUE_FALSE.

Не делать free-text AI grading в must-have: это создаёт лишнюю неопределённость для live-demo.

Каждый вопрос содержит:

- prompt;
- options;
- correct option;
- explanation;
- points.

Клиент до finish не получает correct option.

---

## 6.3. Attempt

Статусы:

- IN_PROGRESS
- COMPLETED
- ABANDONED

У одного пользователя может быть несколько practice attempts.

Один конкретный Attempt может быть завершён только один раз.

Completed attempt immutable с точки зрения ученика.

---

## 6.4. Score

Базовая формула MVP:

`baseScore = round((earnedQuestionPoints / totalQuestionPoints) * 1000)`

Диапазон:

`0..1000`

Для честности duel speed не добавляется прямо в основной score. Время используется как tie-breaker.

---

## 6.5. XP

Предлагаемая детерминированная формула:

`baseXp = 20`

`accuracyXp = round(accuracyPercent * 0.6)`

`perfectBonus = 20`, если accuracy = 100%.

`duelWinnerBonus = 30`, если пользователь победил в duel.

Обычная завершённая практика:

`xp = baseXp + accuracyXp + perfectBonus`

Максимум без duel bonus: 100 XP.

Все значения должны находиться в одном backend calculation module и не дублироваться во frontend.

---

## 6.6. Level

Для MVP:

`level = floor(totalXp / 500) + 1`

Frontend получает готовые `level`, `currentLevelXp`, `nextLevelXp`.

---

## 6.7. Streak

Учебный день определяется выбранной продуктовой timezone.

Для hackathon рекомендуется одна фиксированная timezone проекта.

Правила:

- первая завершённая валидная активность → streak = 1;
- ещё одна активность в тот же календарный день → streak не меняется;
- активность на следующий календарный день → streak + 1;
- пропущен минимум один полный день → streak сбрасывается на 1.

Backend должен хранить `lastActivityDate`.

---

## 6.8. Topic mastery

Для MVP mastery рассчитывается по последним N завершённым attempts ученика по topic.

Рекомендуем N = 5.

`mastery = weighted average accuracy`

Можно упростить до среднего accuracy последних пяти попыток.

Категории:

- 0–39: WEAK
- 40–69: LEARNING
- 70–89: GOOD
- 90–100: MASTERED

---

## 6.9. Weak topic класса

Topic считается weak, если:

- есть минимум 3 completed attempts;
- average accuracy < 60%.

Для маленького demo-класса порог количества attempts можно сделать configurable/demo-friendly.

# 8. СВЯЗИ СУЩНОСТЕЙ

SchoolClass:

- has many ClassMembership
- has many Subject
- has many StudentStats

- belongs to SchoolClass
- has many Topic

- belongs to Subject
- has many Challenge
- has many TopicProgress

Challenge:

- belongs to Topic
- has many Question
- has many Attempt
- may have many Duel

Question:

- belongs to Challenge
- has many QuestionOption

Attempt:

- belongs to User
- belongs to Challenge
- optionally belongs to Duel
- has many AttemptAnswer

Duel:

- belongs to Challenge
- belongs to challenger
- optionally belongs to opponent
- references challengerAttempt
- optionally references opponentAttempt

StudentStats:

- belongs to User
- belongs to SchoolClass

XpLedger:

- belongs to User
- belongs to SchoolClass

29. ТРАНЗАКЦИОННАЯ ЗАЩИТА И КОНКУРЕНТНОСТЬ

Это один из главных технических блоков проекта.

29.1. Finish Attempt

Риск:

два HTTP-запроса finish одновременно.

Без защиты:

XP начислится дважды;
completedChallenges +2;
streak изменится дважды;
ledger получит дубликаты.

Требование:

операция должна рассматриваться как единая бизнес-транзакция.

В рамках одной защищённой операции:

проверить Attempt;
убедиться, что он не обработан;
рассчитать результат;
сохранить answers/result;
создать XP ledger;
обновить StudentStats;
обновить TopicProgress;
завершить Attempt;
если duel — инициировать duel resolution.

Ключ блокировки логически привязан к attempt/user.

29.2. Accept Duel

Риск:

один shareCode одновременно открыли два человека.

Без защиты оба могут стать opponent.

Требование:

в одной Serializable операции:

прочитать duel;
проверить WAITING;
проверить expiry;
проверить self-duel;
закрепить opponent;
создать opponent attempt;
изменить статус ACTIVE.

Только один запрос успешен.

29.3. Complete Duel

Риск:

finish/retry/event приводит к повторному определению победителя и повторному bonus XP.

Требование:

Duel COMPLETED является terminal state.

Winner XP ledger должен иметь уникальный source.

29.4. Join Class

Риск:

double click/retry создаёт два membership.

Требование:

уникальность (classId, userId) + безопасное повторное поведение.

29.5. XP Ledger

XP нельзя просто делать:

stats.totalXp += amount

без записи причины.

Каждое начисление должно иметь source.

Это позволяет доказать жюри, что reward system защищена от повторных запросов.

42. РИСКИ И НЕСТАНДАРТНАЯ ЛОГИКА
Риск 1. AI API упал во время demo

Решение продукта:

fallback generation.

Если provider недоступен, demo environment может использовать заранее подготовленный challenge по известной topic.

Риск 2. AI вернул неправильный JSON

Нельзя сохранять как есть.

Нужна строгая server-side validation.

Challenge становится READY только после полной проверки.

Риск 3. Double finish

Самая опасная бизнес-гонка.

Последствия:

duplicate XP;
duplicate streak;
corrupted leaderboard.

Обязательная транзакционная защита.

Риск 4. Race при Accept Duel

Два пользователя могут одновременно принять challenge.

Только один должен стать opponent.

Обязательная транзакционная защита.

Риск 5. Повторное начисление duel bonus

Duel resolution должен быть идемпотентным.

XpLedger должен защищать source от дублей.

Риск 6. Timezone streak

24 часа и следующий календарный день — не одно и то же.

Нужно заранее выбрать timezone продукта и использовать календарную дату.

Риск 7. Утечка correct answers

Если /challenge/:id возвращает isCorrect, пользователь может открыть DevTools и увидеть ответы.

Student DTO обязан исключать grading data.

Риск 8. Client-side score

Нельзя доверять score из браузера.

Клиент отправляет только выбранные option IDs.

Backend рассчитывает результат.

Риск 9. Leaderboard consistency

Leaderboard должен отражать server state.

Для demo Redis cache либо инвалидируется после XP mutation, либо используется короткий TTL.

Риск 10. Удаление сущностей

Hard delete Topic/Challenge после attempts ломает историю.

В MVP использовать archive semantics для сущностей с историческими данными.

Риск 11. Маленький demo dataset

Analytics с одним пользователем выглядит бессмысленно.

Нужны seed attempts/stats до презентации.
